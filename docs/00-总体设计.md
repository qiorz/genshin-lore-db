# 00 · 总体设计

## 1. 一句话目标

建立一个**本地优先、证据可回溯、支持中文全文检索**的原神叙事资料库，用来回答三类问题：

1. 这句话/这段剧情原文是什么？出自哪里？
2. 这个人物、组织、地区、事件在哪些文本里出现过？
3. 关于某个设定，有哪些说法？谁说的？是否互相矛盾？

它服务的不是“打怪配队”，而是“理清世界观”。

---

## 2. 目标与非目标

### 目标

- 收集**叙事性文本**：魔神任务、传说任务、世界任务、活动剧情、邀约、间章、书籍、角色故事、武器/圣遗物故事、地理志、关键道具描述、官方公告。
- 保留**来源与版本**：URL、页面 ID、修订号、抓取时间、游戏版本、转写保真度。
- 建立**段落级引用**：不是“某篇文章里提到”，而是“某篇第 3 节第 12 行”。
- 支持**中文检索**：人物、地名、专有名词、台词片段。
- 支持**剧透过滤**：按主线进度/地区/角色过滤。
- 允许**矛盾共存**：同一设定可以有多个说法，分别标注来源和可信度。
- 最终形成**可维护的知识层**：实体、别名、关系、事件、时间线、claims。

### 非目标（第一版不做）

- 不做公开网站、不做商业化；仓库公开托管只用于保存原始资料，不另建镜像站或下载服务。
- 不追求“全游戏每一句 NPC 闲谈”的即时全量。
- 不做自动剧情总结或自动考据结论。
- 不依赖云端数据库或在线 API 才能阅读。
- 不把 Wiki 的“攻略/配队/刷材料”内容混进叙事库。
- 不把图片 OCR 当作默认能力；图片文本单独标记，必要时人工补录。

## 3. 为什么这件事比“爬几个页面”难

### 3.1 文本分散且形态不一

- BWiki 的任务页是**系列任务 + 子任务**两层，正文在子任务页的 `==任务剧情==` 里；
- 书籍页是模板字段 + `<br>` 长文本；
- 角色页混有属性、配队、语音、故事，必须拆开；
- 米游社帖子是 HTML，很多信息在图里；
- 官方站点是 JS 渲染，不能只抓 HTML 壳。

### 3.2 Wiki 文本不是“原生游戏文本”

Wiki 可能：

- 把多语言文本混在一起；
- 改写、省略、合并选项；
- 用模板/颜色/折叠块包裹台词；
- 漏掉版本更新后的新增段落；
- 把玩家注释混进正文。

因此必须记录 `transcription`（逐字、近逐字、编辑过、摘要），不能把“Wiki 页面”直接等同于“官方原文”。

### 3.3 原神的叙述本身不可靠

游戏里大量文本是：

- 角色主观视角；
- 道听途说、宣传、宗教经典；
- 故意误导、删改、隐喻；
- 不同版本/不同世界线/不同角色的记忆。

所以数据库不能只存“事实”，还要存“**谁在什么文本里声称了什么**”。这是 `claims` 表存在的理由。

### 3.4 时间线有两套

- **现实时间**：版本 1.0、1.1……实装顺序；
- **提瓦特时间**：魔神战争、葬火之战、坎瑞亚灾变、当前时间。

两者不能混。`documents.version` 记现实版本，`timeline_entries` 记世界观时间；`events` 同时保留 `time_certainty`（确切/约略/相对/未知）。

### 3.5 中文检索不是默认就好

SQLite FTS5 的 `unicode61` 会把连续汉字当成一个 token，直接搜“钟离”可能搜不到“钟离说”。当前方案（2026-11-12 第 24 步定型）：

- `sections_fts` 用 `trigram`，支持 3 字以上中文子串检索；
- `sections_fts_words` 用 `unicode61` 索引 jieba 预分词的 `body_segmented`，负责 2 字词，
  查询与导入共用同一份 `manifests/terms.txt` 用户词典，保证切词口径一致；
- `body_segmented` 必须是分词结果，导入时不要加 `--no-segment`；
- 两套索引都没命中时用 `LIKE` 兜底（单字查询也走这里）；
- 保留标题 `LIKE` 匹配，避免书名只在标题里出现时搜不到。

### 3.6 版本变化与页面漂移

同一页面会随版本更新。必须保存：

- `retrieved_at`；
- Wiki `revision_id`；
- `content_hash`；
- 原始响应（`raw/`）。

否则以后无法判断“是文本变了，还是我记错了”。

## 4. 架构

### 4.1 分层

```text
┌─────────────────────────────────────────────────────────┐
│ 来源层：官方站点 / 米游社 / 观测枢 / BWiki / 数据包 / 其他 Wiki │
└───────────────────────┬─────────────────────────────────┘
                        │ 抓取（限速、缓存、记录元数据）
                        ▼
┌─────────────────────────────────────────────────────────┐
│ 证据层 raw/：HTML、JSON、wikitext 原样保存，只增不改       │
│ 每个文件配一个 .meta.json：URL、时间、状态码、哈希、修订号  │
└───────────────────────┬─────────────────────────────────┘
                        │ 解析、清洗、分段、去模板
                        ▼
┌─────────────────────────────────────────────────────────┐
│ 阅读层 corpus/：Markdown + YAML front matter             │
│ 人可读、可 diff、可被 Obsidian 直接打开                   │
└───────────────────────┬─────────────────────────────────┘
                        │ 分词、入库、建引用
                        ▼
┌─────────────────────────────────────────────────────────┐
│ 索引层 db/：SQLite                                      │
│ documents / sections / entities / claims / FTS5          │
└───────────────────────┬─────────────────────────────────┘
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
   Obsidian 阅读     SQL/CLI 检索      exports/ 主题导出
                        │
                        ▼
┌─────────────────────────────────────────────────────────┐
│ 知识层 knowledge/：实体、关系、事件、时间线、考据          │
│ 人工整理，引用阅读层/索引层的证据，不替代证据               │
└─────────────────────────────────────────────────────────┘
```

### 4.2 为什么正文和知识层分开

- 正文是**证据**，应该尽量保持原样；
- 知识层是**解释**，会随理解变化；
- 如果把“我认为钟离是……”写进正文，以后无法区分原文和推论；
- 分开后，可以重写知识层而不动原文，也可以换一版时间线而不破坏引用。

### 4.3 为什么用 Markdown + SQLite 双存储

- Markdown：可读、可 diff、可用 Obsidian、不会被数据库锁死；
- SQLite：全文检索、结构化过滤、覆盖统计、引用关系；
- 两者通过 `doc_id`、`section_id` 和 `content_hash` 对齐；
- 不把正文只存数据库，也不把检索只交给文件系统。

## 5. 核心数据模型

### 5.1 `documents`：一篇可引用的文档

一条记录代表“一篇任务/一本书/一个角色页/一把武器”，字段包括：

- `doc_id`：稳定 ID；
- `doc_type` / `subtype`：任务/书籍/角色/武器/圣遗物/地区/公告；
- `title` / `title_en`；
- `language`、`region`、`version`；
- `canon_status`：官方、官方二手、社区转写、数据包、玩家考据；
- `transcription`：逐字、近逐字、编辑过、摘要、未知；
- `spoiler_level`；
- 来源、URL、修订号、抓取时间、原始路径、清洗后路径、哈希。

### 5.2 `sections`：段落/台词

一条记录代表一个标题、一段正文、一句台词或一个选项：

- `doc_id` + `ordinal` 决定顺序；
- `parent_id` 支持“章节 → 小节 → 台词”的层级；
- `speaker` 记录说话者；
- `body` 原文，`body_segmented` 分词后文本；
- `source_line` 记录在原始 wikitext/HTML 中的行号（可选）。

这样引用可以精确到“某任务某一步的某一句”。

### 5.3 `entities`：世界中的对象

人物、国家、组织、地点、概念、生物、物品、事件都可以是实体。每个实体有：

- 稳定 `entity_id`；
- 类型；
- 规范名（中文）；
- 描述；
- 剧透等级；
- 多个别名（`entity_names`）：本名、称号、化名、译名、拼音。

### 5.4 `entity_relations`：实体间关系

例如：

- `钟离` —`member_of`→ `往生堂`；
- `钟离` —`is`→ `摩拉克斯`；
- `璃月` —`located_in`→ `提瓦特`；
- `坎瑞亚` —`destroyed_by`→ `天理`（需标注说法来源）。

关系表存“整理后的断言”，`claims` 表存“文本中的原始说法”，二者可以互相校验。

### 5.5 `claims`：谁说了什么

一条 claim 至少包含：

- 主体、谓语、客体（实体或字面值）；
- 原始陈述/摘要；
- **视角**（谁相信/谁声称）；
- 来源文档 + 段落；
- 可信度与状态（开放/接受/争议/否定/被取代）；
- 剧透等级。

例：

```text
subject: 坎瑞亚
predicate: 覆灭原因
object_literal: 触怒天理/接触禁忌知识/……
perspective: 某本书/某角色
confidence: disputed
source: 某书籍某卷
```

这不是为了“自动判定真相”，而是为了把不同说法并置，方便比较。

### 5.6 `events` + `timeline_entries`：事件与时间

- `events`：事件本身（名称、类型、年代、描述）；
- `timeline_entries`：在时间轴上的位置，允许 `relative_time`、`absolute_year`、`sort_key`；
- `time_certainty`：确切/约略/相对/未知。

时间线是**解释层**，不是原文；一条时间线记录应能追溯到至少一个来源。

## 6. 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 主存储 | Markdown + SQLite | 可读、可版本控制、可检索 |
| 正文粒度 | 段落/台词级 | 引用精确，便于 claims 关联 |
| 中文检索 | FTS5 trigram + 2 字 LIKE 兜底 | 比默认 tokenizer 更适合中文 |
| 原文保存 | 只增不改 + 哈希 | 可回溯、可对比 |
| 知识表达 | 实体 + 关系 + claims | 允许矛盾，不强行唯一真相 |
| 来源策略 | 观测枢结构化主源，BWiki 校验/兜底 | 任务对话图/书籍/角色模块最结构化；BWiki 覆盖广，适合交叉核对 |
| 首批范围 | 主线 + 书籍 + 角色 | 信息密度最高，覆盖世界观主干 |
| 剧透 | 四级 + 范围标签 | 可按进度过滤，而不是简单隐藏 |
| 部署 | 本地 | 版权、隐私、可维护性 |

### 为什么不是“先建一个大知识图谱”

没有语料和引用，图谱只能靠记忆和二手总结，最后会变成“看起来很完整、但每条都不可核对”的设定集。正确顺序是：

```text
语料 → 引用 → 实体/关系 → 时间线 → 更高层考据
```

### 为什么不是“先写全量爬虫”

页面结构、模板、限流、图片化文本、版本差异都会变。先用 15–20 篇验证解析器和格式，再扩量，返工成本最低。

## 7. 成功标准

第一版（试点）完成时，应能：

- [ ] 用一条命令抓取并保存 15–20 篇不同来源/类型的文本；
- [ ] 生成符合规范的 Markdown，front matter 校验通过；
- [ ] 导入 SQLite，`sections` 能精确到台词；
- [ ] 搜“钟离”“坎瑞亚”“葬火之战”能返回相关段落和出处；
- [ ] 每篇正文至少有一个可点击来源；
- [ ] 重复抓取不会产生重复文档；
- [ ] 能按 `region`、`version`、`spoiler_level` 过滤；
- [ ] 人工抽查 10 段，文本与来源一致。

第二版（叙事文本全量）完成时，应能：

- [ ] 覆盖全部魔神任务、传说任务、世界任务、活动剧情、书籍、角色故事；
- [ ] 输出覆盖矩阵，标出缺失/待补页面；
- [ ] 版本更新后生成“变更清单”，而不是全量重抓；
- [ ] 为核心 50 个实体建立别名和基本关系；
- [ ] 建立一条可追溯的提瓦特时间线。

## 8. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 站点反爬/限流 | 抓取中断 | 限速、缓存、断点续跑、优先 API |
| 页面结构变化 | 解析失败 | 原始快照保留，解析器可重跑；按页面类型分开 |
| Wiki 文本被改写 | 设定失真 | `transcription` 标注；关键段落对照官方/数据包 |
| 图片化文本 | 漏内容 | 标记 `needs_ocr`，人工补录；不默认 OCR |
| 版本更新 | 文本过期 | `version` + `retrieved_at` + 哈希 + diff |
| 文本量过大 | 无法维护 | P0/P1/P2 分层，先叙事后道具 |
| 版权 | 不能公开 | 本地使用；公开只发索引/考据/短引用 |
| 时间线争议 | 结论不可靠 | `claims` + `certainty`，不强行统一 |
